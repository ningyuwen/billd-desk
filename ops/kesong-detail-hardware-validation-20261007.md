# 可颂详情进入与返回卡顿复测

2026-10-07；分支 `p/ningyuwen/web-remote-stats`。本轮核对并获取 `origin/develop`，未提交、推送、合并或更新线上下载。

## 结论

卡顿仍存在，不能判定为已修复，更不能用此前连续滚动的 53–59 解码 fps 证明详情动画流畅。

本轮确认软件 VP8 存在 CPU 限制，改为设备支持时优先协商硬件 H.264 Baseline，保留其他格式作为回退。最终手机实际编码器为 `c2.qti.avc.encoder`；这证明编码路径改变，不证明硬件编码一定更快或已经消除卡顿。

进一步记录表明发送排队、接收帧迟到仍然明显；源端可颂自身也存在较长帧耗时。临时关闭额外帧预算、缩短发送排队目标、提高起始带宽的试验都没有得到稳定收益，最终源码撤回这些实验参数。

## 测试条件与方法

- Xiaomi 24122RKC7C、Android 16；真实 Mac `/Applications/BilldDesk.app` 控制手机。复用既有权限和会话确认流程，保留系统屏幕共享保护。
- 固定推荐 Feed 中两件图文作品：「这个假期，你的选择会是广州吗？」和「无法和咖啡分手的女人。」；不刷新 Feed，正常返回原任务。
- 主对照为实际视频尺寸 1080×2400、目标上限 60 fps、最高 12000 kbps。另对照 6000 kbps、30 fps，未发现稳定消除卡顿。
- 在 Mac 点击作品和系统“返回”，每个操作独立采样约 2 秒：Android 捕获时间戳、编码帧、编码器、编码累计耗时和发送累计排队；Mac RTP 计数及 `requestVideoFrameCallback` 的时间、媒体时间和呈现帧序号。仅通过显式启动参数 `--billd-performance-log` 开启，不记录画面、文本、连接密码、SDP、ICE 地址或中继凭证。
- Mac 日志只接收白名单动作和有限长度的数值数组，保存到用户日志目录，权限 0600。常规启动不开启操作采样。
- 另用同一作品测不共享与共享时的源端 `dumpsys gfxinfo ... framestats`，每次重置计数并核对 Activity；此组用 ADB 输入，不作为 Mac 点击延迟测量。

## 发送与接收结果

软件 VP8 对照中，一次城市作品操作在 2 秒内编码 102 帧，累计编码耗时增加 1.703 秒；后来一次咖啡作品进入捕获 37 帧、仅编码 1 帧，报告 `qualityLimitationReason=cpu`。原始捕获时间戳的绝对偏移因时钟不同而无效，只能使用其间隔；后续采样已统一为 `System.nanoTime()`。

最终 Android `0.1.20`，两件作品各进入和返回 3 轮，12 个窗口均为硬件 H.264，质量限制原因为 `none`。实际数据如下，计数为操作后 2 秒窗口的增量，含动画、静止和迟到帧，不能除以 2 当作动画的真实 fps。

| 作品与操作 | 三轮解码帧增量 | 三轮回调数 | 三轮解码丢帧增量 |
| --- | --- | --- | --- |
| 城市进入 | 81 / 40 / 67 | 73 / 38 / 52 | 0 / 0 / 0 |
| 城市返回 | 10 / 88 / 48 | 11 / 76 / 42 | 0 / 0 / 0 |
| 咖啡进入 | 9 / 20 / 16 | 9 / 19 / 16 | 0 / 0 / 0 |
| 咖啡返回 | 21 / 24 / 25 | 20 / 21 / 24 | 0 / 0 / 0 |

进入后的首个呈现回调为城市 322 / 147 / 147 ms，咖啡 290 / 105 / 188 ms。这不是点按到详情完整显示的延迟，因为首个回调可能仍为旧页面。

筛选呈现序号连续、媒体时间间隔小于 100 ms 的帧，进入窗口的最大呈现间隔为城市约 100 / 75 / 92 ms，咖啡约 75 / 83 / 92 ms。仍明显偏离 60 fps 的 16.7 ms 间隔；未把静止期间的大间隔直接计为掉帧，也未把漏回调当作屏幕漏呈现。

发送端按 `ΔtotalPacketSendDelay / ΔpacketsSent` 计算每个操作窗口的平均包排队，最终范围约 30–1324 ms。城市第二次进入编码 114 帧，Mac 此窗口解码 40 帧，随后返回窗口解码 88 帧，支持“画面迟到”的判断。编码与接收窗口时刻并非完全相同，不能据此精确计算丢失帧数。

收紧发送队列的临时版本出现新增解码丢帧，撤回。其他参数试验及版本仅留作本地对照，不作为发布配置。

## 源端与证据边界

未共享时，咖啡作品三轮进入均报告 3 个 janky frames，P95 为 48 / 69 / 65 ms；所以源端本身并非始终流畅。最终 `0.1.20` 共享时，同一作品三轮进入也均为 3 个 janky frames，P95 为 57 / 53 / 65 ms；城市作品三轮进入均为 2 个 janky frames，P95 为 13 / 23 / 22 ms。这些短窗口未证明共享显著恶化源端绘制，但不能排除捕获、编码、发送与呈现环节的问题。`gfxinfo` 可能聚合多个窗口，不能把总帧数直接当作手机屏幕 fps。

原始记录位于被 Git 忽略的 `android-release/detail-transition-20261007/`，包含 `remote-transitions.json`、白名单数值日志、各版本发送采样、源端 framestats 和实际客户端截图。Mac 截图只证明当时显示的页面，不证明动画流畅。

未进行外部相机/物理刷新测量，未测其他手机、跨网络中继、长时间视频、Windows 或本轮网页版。多次升级中旧 Mac 会话曾失效，完全退出并重建会话后恢复；尚未确定失效原因，不归因于编码器。运行验证通过的是操作和连接，性能仍未达到流畅标准。
