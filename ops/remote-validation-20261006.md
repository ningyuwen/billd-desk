# 安卓控制 Mac 实机验证

日期：2026-10-06，时区 Asia/Shanghai。使用原安卓手机上的 BilldDesk 0.1.3 和 `/Applications/BilldDesk.app` 正式版0.0.1，连接当前私有服务器。

| 项目 | 结果和证据 |
| --- | --- |
| 保存设备一键连接 | 通过；无需再次输入设备代码或密码，自动进入横屏全屏控制页。 |
| Mac 屏幕采集和安卓视频接收 | 通过；实际画面3342×2160，安卓帧接收与渲染日志持续更新。 |
| 远程触控和文字输入 | 通过；手机点击 Mac 输入框，发送 `Desk`，Mac 输入框实际出现该文字。测试文字已清除。 |
| 主动断开 | 通过；手机回到设备页，Mac 显示“已准备好连接”。 |
| 安卓 App 重启与重连 | 通过；强制停止并重启安卓 App 后，保存设备仍可一键重连，设置保留2160P、60 fps、20 Mbps上限。 |
| 长时间连接和空闲锁屏观察 | 通过；10:56:25–11:02:25每30秒采样，共13次；6分钟内持续收到画面，系统始终未锁屏，最后系统空闲时间452秒。 |
| 长测后远程控制 | 通过；再次通过手机触控与文字输入，在 Mac 输入框确认 `Desk`，随后清除。 |

本次稳定接收和渲染采样约37–38 fps，连接初期部分采样约34 fps。60 fps是请求值，不代表实际帧率。Mac `RTCRtpSender` 上限为20000000 bps，采集轨道设置3342×2160、60 fps；编码统计显示 `qualityLimitationReason: cpu`，本次没有达到60 fps。

保活脚本运行期间，系统11:00:09检查到空闲324.5秒超过描述文件的300秒，随后记录 `PMDisplaySleepIsBlocked`，具体阻止方为 `caffeinate command-line tool`，因此没有启动屏幕保护。本次证明当前 Mac 的临时保活有效，没有修改公司策略；没有进行完整30分钟或更长时间的耐久测试。

测试结束后已断开远程连接，并退出 Mac 测试进程以停止屏幕采集；确认原进程结束后，重新打开客户端，当前显示“已准备好连接”。本次未修改应用源码、未重新打包或部署安装包。
